# Cursor and Grok consumer subscriptions as CodexHub upstreams: OAuth / token-reuse evidence

Date: 2026-08-14
Scope: Desk research only. This note records whether the Cursor (Pro/Ultra) and Grok (SuperGrok / X Premium+) consumer subscriptions could serve as CodexHub upstreams by reusing the consumer client's login state, the same pattern as the existing ChatGPT-subscription Responses proxy. It does not add, imply, or authorize a production route, a client auto-configuration, or any credential extraction from the local machine. No real tokens, cookies, or credentials were read or used for this note.

## Evidence boundary and source pins

Primary sources are official vendor pages, official documentation, official legal text, and statements by vendor staff on the vendor's own support forum, accessed 2026-08-14 unless noted otherwise. Community projects, third-party docs, blogs, and issue trackers are secondary evidence and are marked as such. Two xAI legal pages returned HTTP 403 to the fetcher; their text was pinned from the Internet Archive Wayback Machine snapshot of the canonical URL and is cited with both URLs.

## Cursor: verified official surface

- There is **no official OAuth flow for third-party applications** and **no official programmatic raw-model API tied to the subscription**. The official programmatic surfaces are the Cursor CLI (`agent`), the Agent SDK, and the Cloud Agents API — and Cursor staff state all of these "always run the Cursor agent harness. They don't give you the raw model" (forum thread 164676). The public REST APIs (Admin, Analytics, AI Code Tracking, Bugbot, Cloud Agents) are explicitly not model-inference or chat-completion APIs (cursor.com/docs/api).
- The CLI authenticates with browser login (the subscription account) or with a user API key (`CURSOR_API_KEY`) from the dashboard (cursor.com/docs/cli/reference/authentication). Whether CLI/API-key usage is metered separately from the IDE's included plan usage is not stated on the pages reviewed — UNVERIFIED. The pricing page only commits to "Every plan includes a set amount of model usage" plus on-demand overage billed in arrears.
- ToS §1.5 prohibits reverse engineering or deriving the underlying structure of the Service, probing it, scraping/extracting, and renting/leasing/selling it; §9 permits termination without refund for violations.
- Enforcement stance is not theoretical: Cursor staff on the official forum state twice (2026-07-04 and ~2026-08-11) that using the subscription outside official clients via private endpoints violates the Use Restrictions and "can trigger abuse enforcement, up to and including an account ban," and that even a personal local-only proxy "doesn't change the analysis." A public OpenAI-compatible endpoint is an acknowledged open feature request, not a shipped product.

## Cursor: unofficial surface (secondary evidence)

- Auth artifact reused: historically the `WorkosCursorSessionToken` web cookie (cursor-api fork family, 2024–2025, largely stale); more recently the desktop/CLI OAuth access token against Cursor's private, non-public Connect-RPC/protobuf agent endpoints (composer-api, Oh My Pi `cursor` provider).
- Upstream protocol mimicked: Cursor's internal aiserver client protocol; projects translate it to OpenAI Chat Completions with streaming.
- Maintenance/breakage: the cookie-based family is a cluster of stale forks; the token-based tools are newer but were publicly named by Cursor staff as ToS violations, so both breakage and enforcement pressure are expected. No credible volume of individual ban reports was found beyond the staff statements and generic "suspicious activity" blocking write-ups (Apidog blog, secondary) — the enforcement evidence is the vendor's own stated policy, not a documented ban wave.

## Grok / xAI: verified official surface

- **An official subscription-OAuth path exists.** xAI's own news page announces SuperGrok / X Premium login inside the third-party agent OpenClaw (device-code supported), on every tier, with more agent integrations promised (x.ai/news/grok-openclaw). xAI's first-party Grok Build CLI authenticates via browser OAuth on first launch (docs.x.ai/build/overview).
- The consumer FAQ officially accounts subscription usage across "API, Build, Chat, Imagine, Voice" in one weekly pool (docs.x.ai/grok/faq), which is consistent with subscription-backed programmatic (API-surface) usage under OAuth. Separately purchased prepaid "API credits" exist and are non-refundable; the metered API-key track (console.x.ai, `XAI_API_KEY`, Enterprise Terms) remains a distinct billing ledger.
- Endpoint-level mechanics of the OAuth flow (auth.x.ai authorize/token endpoints, PKCE, device code, scopes `grok-cli:access api:access`, bearer use against `https://api.x.ai/v1` Responses-style) are **not published in xAI's own docs** as of this access date; they are pinned from multiple consistent community implementations (Hermes Agent, sub2api, OpenCode v1, Warp, LobeHub — all secondary). Whether xAI offers open third-party OAuth client registration, or third parties must reuse the Grok CLI's public client identity, is UNVERIFIED.
- ToS/AUP: no sharing account credentials (Consumer ToS); the AUP prohibits bots/automated non-human access, reverse engineering, rate-limit circumvention, and reselling, with suspension/termination as the stated consequence. The AUP's automation clause is in visible tension with xAI's own announced agent integrations; the officially announced pattern (interactive user OAuth login, per-user token, product surfaced as an agent) is the sanctioned reading, while unattended credential harvesting (cookie scraping, account farms) is the prohibited one.

## Grok / xAI: unofficial surface (secondary evidence)

- Cookie path: grok2api-family projects reuse the grok.com `sso` web cookie, pool multiple accounts, and expose OpenAI-compatible chat completions. chenyme/grok2api is actively maintained; forks and deployment blogs are numerous. Practitioner reports describe xAI banning pooled `sso` tokens within days, and an ecosystem of mass-registration tooling exists around it — classic cat-and-mouse. This path is a clear AUP violation (automated access, scraping-adjacent, credential sharing when pooled).
- OAuth path: Hermes Agent (`xai-oauth`), OpenCode v1, pi-xai-oauth, sub2api, CoWork, Warp, and LobeHub implement or ship PKCE/device-code login with refresh against `api.x.ai/v1`. Hermes documents observed `HTTP 403` gating on some SuperGrok tiers (issue reference in their docs) — entitlement enforcement exists but is tier/plan-scoped, not a blanket ban on the flow.

## Gateway feasibility mapping for CodexHub

### Cursor

- OAuth/token-reuse integration path: **none official.** Unofficial only, via cookie (`WorkosCursorSessionToken`) or client access token against private Connect-RPC agent endpoints.
- What unofficial integration would require: extracting a short-lived browser cookie or desktop token; re-implementing Cursor's private aiserver Connect-RPC/protobuf chat surface; translating Connect-RPC streaming to OpenAI Responses/Chat Completions including tool calling; surviving unannounced protocol changes; and accepting that Cursor has publicly named this exact pattern a ToS §1.5 violation with account-ban enforcement.
- **Recommended stance: do-not-do.** There is no gray zone to exploit — the vendor's staff have answered this exact question twice on the official forum. The only ToS-clean programmatic use of a Cursor subscription is wrapping the official `agent` CLI / Agent SDK (agent-harness latency and behavior, not a raw model), which does not fit CodexHub's "subscription-backed model upstream" pattern and is out of scope for this research question.

### Grok / xAI

- Integration path: **officially anchored OAuth exists.** A per-user PKCE/device-code login against xAI yields a bearer token usable on `https://api.x.ai/v1`, which exposes a Responses-style surface — the same protocol family CodexHub already proxies for the ChatGPT subscription. Usage bills against the subscriber's weekly pool, not a separate API-key ledger. This mirrors xAI's announced OpenClaw integration and is shipped by multiple independent tools.
- What integration would require: implement (or delegate to `grok login`) the OAuth flow with refresh-token handling; call `api.x.ai/v1` Responses endpoints — likely minimal protocol translation for a Responses-first gateway; respect that subscription quota is a shared weekly pool with per-tier entitlement gating (observed 403s on some tiers).
- Risks: no published third-party OAuth client registration (existing tools reuse the first-party public client identity — policy could tighten); the AUP automation clause gives xAI a lever against abusive/unattended use; tier gating and endpoint drift are observed. None of these resemble the Cursor situation: the flow itself is operated and advertised by xAI.
- **Recommended stance: experimental-only, OAuth-only.** Support a per-user interactive login (device-code for headless) against the official xAI OAuth surface, clearly labeled experimental, never pooling accounts, never touching the grok.com `sso` cookie. The cookie-based grok2api pattern is do-not-do.

## Verdict

- **Cursor: NO.** No official OAuth, no raw-model API, explicit staff-confirmed ToS prohibition with ban enforcement on subscription use outside official clients. Do not integrate; revisit only if Cursor ships the requested public OpenAI-compatible endpoint or a third-party OAuth program.
- **Grok: YES, with discipline.** xAI officially operates a subscription-backed OAuth surface (Grok Build first-party; OpenClaw announced; weekly-pool accounting documented). An experimental CodexHub upstream using per-user xAI OAuth against `api.x.ai/v1` is the same integration shape as the existing ChatGPT route and is defensible; the reverse-engineered `sso`-cookie path is a clear AUP violation with active token bans and must not be used.

Open items: whether xAI will publish third-party OAuth client registration (UNVERIFIED today); exact SuperGrok tier entitlements for OAuth API access (observed 403 gating, secondary); Cursor CLI quota accounting relative to plan usage (UNVERIFIED).
