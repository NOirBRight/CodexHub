CodexHub 深模块问题图

问题不是文件太长，而是策略穿过了错误的 seam：调用者必须知道实现细节。本页只读讨论用，不改变 0.1.9-beta.2 发布候选。

Interface 调用者必须学会的 现在泄漏出去的 应藏进实现的

深 vs 浅

现在

浅模块

很大的接口：16 个参数 / 70 个命令 / 20 个 setter
薄实现：转发、match、getattr、页面复制 Toast

删除这个模块后，复杂度不会消失，会散回每个调用者和测试。

目标

深模块

很小的接口：connect / prepare / commit
大量行为：adoption、fingerprint、协议转换、terminal-once、精确 restart

删除这个模块后，同样的复杂度会在 N 个调用者里重新长出来。这才说明它赚回了存在价值。

四块问题，一个个谈

1

Python Gateway：假深度

RoutePlan 看起来是深模块，实际通过 _proxy_attr 反向依赖 codex_proxy.py。规划事实仍住在 HTTP facade 里。

2

Rust 客户端集成：一个真 seam，五个旧分支

injection.rs 已经把 DSH 的 inject/detach/readback 藏好了。Pi / OpenCode / OMP / ZCode 仍散落在 gateway.rs 的 match arms 里。

3

前端工作流：策略复制进页面

Toast 生命周期和精确 restart 披露不是模块，是复制。DSH / Codex / 其他客户端有三套连接实现。

4

发布与运行时：策略写在脚本里

Windows 与 Linux 产物、Python 3.13 选择、evidence envelope 各算一遍。没有一个 ReleasePlan 作为 Interface。

第十一项：ClientConnection

ADR-0004：connect/disconnect 就是 inject/detach，从不做 Activation。前端现在是三套实现。建在 PersistentAction 之上；RestartTarget 由后端报告返回，页面不猜。

  -> Promise<{ restart: RestartTarget }>
disconnect(target)
  -> Promise<{ restart: RestartTarget }>
// stale 的 repair 就是再调 connect()
